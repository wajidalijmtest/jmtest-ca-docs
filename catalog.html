Catalog: how products get into the Consolidated Database

Three sources feed the catalog: Sage 100 items, Business Central CAD pricing, and a one-time seed. Sage 100 items and Business Central prices both pass through the ERP-Sync Job. Only the Seeders write to the Consolidated Database (CDB) directly. This page covers each source, one sync run from start to finish, which column comes from where, and how the storefront uses the result.

1The whole flow

Three sources, one writer

JMTS IT pushes the Sage 100 item extract into staging.item_code, a temporary store the storefront never reads. The ERP-Sync Job reads the new staging rows, pulls CAD pricing and the other Canadian fields from the Business Central Custom API, and writes the result into the catalog tables. The Seeders ran once to load the starting catalog. After that, every change to an ERP field comes through the ERP-Sync Job.

Source system Staging table Writes to the CDB Consolidated Database
Only two things write the catalog.Sage 100 items and Business Central prices both pass through the ERP-Sync Job. Only the Seeders write to the CDB directly, and only once. The storefront, the CMS and the outbox job never change an ERP field. product_erp_refs (JMTS IT) and calibration_rules (calibration lab) are kept by people and only read by the job.

2One sync run

jobs/erp-sync, start to finish

Each run does the Sage 100 part first, then the three Business Central pulls. Every write is an upsert or a replace, so a run that stops half-way can simply run again.

4Step by step

SQL is a sketch of what each step does, not the final migration. Column names are from the data model; values are illustrative.

Sage 100 items

JMTS IT push, then the ERP-Sync Job

  1. S1
    PUSHJMTS IT pushes the item extractstaging.item_code

    Each push run gets one load_batch_id. Rows are unique on (item_code, warehouse_code, load_batch_id): one row per item, per warehouse, per push. It uses the same push contract as Vaetrix (docs/infra/staging-item-code.sql), so nothing changes on the IT side.

    Two rows from one push: the same item in two warehouses

    item_code         'MEG-1000'              'MEG-1000'
item_code_desc    'Insulation tester 10kV' 'Insulation tester 10kV'
product_line      'INSUL'                 'INSUL'
category          'Insulation testers'    'Insulation testers'
sales_uom         'EA'                    'EA'
standard_price    725.0000                725.0000
suggested_retail  799.0000                799.0000
quantity_on_hand  4.0000                  null      -- null = unknown
warehouse_code    '000'                   'CAL'
item_status       'Active'                'Active'
source_system     'SAGE100'               'SAGE100'
load_batch_id     '0b9e…'                 '0b9e…'   -- same push
row_hash          'a41f…'                 '77c2…'
extracted_at      2026-11-12 02:00        2026-11-12 02:00
processed         false                   false

    Every Sage 100 field that has no column of its own is kept in raw (jsonb), so nothing in the source record is lost and a new mapping can be added later without a new push.

  2. S2
    SQLRead unprocessed rowsstaging.item_code WHERE processed = false

    A partial index on unprocessed rows keeps this read fast however large the staging table grows.

    Query

    SELECT *
FROM   staging.item_code
WHERE  processed = false
ORDER  BY loaded_at, item_code, warehouse_code;
  3. S3
    JOBCollapse warehouses into one itemgroup by item_code within a load_batch_id

    A storefront product is one SKU, but staging has one row per warehouse. The job groups the rows of one item in one batch. Item-level fields (description, product line, category, status) are the same in every warehouse row; stock is combined.

    Combining stock proposed

    any warehouse quantity_on_hand > 0   → in stock
all known quantities = 0             → out of stock
every quantity null                  → unknown, leave in_stock as it was

    Which warehouses count for jmtest.ca is an open decision (§9).

  4. S4
    SQLMatch the item to a storefront SKUcatalog.product_erp_refs, source_system = 'SAGE100'

    Query

    SELECT sku
FROM   catalog.product_erp_refs
WHERE  source_system = 'SAGE100'
  AND  role          = 'sale'
  AND  native_number = 'MEG-1000';

    No row means the item isn't on the storefront. It is reported, not inserted: JMTS IT decides whether it belongs and adds the mapping. The next push then brings it in.

  5. S5
    SQLUpsert the product when something changedcatalog.products

    The job compares row_hash with the last processed rows for the same item. If nothing changed it skips the write and goes straight to S6.

    Upsert, Sage-owned columns only mapping proposed, see §5

    INSERT INTO catalog.products
       (sku, brand_id, product_line, category_id, status, in_stock, updated_at)
VALUES ('MEG-1000', 'jmtest', 'INSUL', 'insulation-testers', 'active', true, now())
ON CONFLICT (sku) DO UPDATE
SET    product_line = EXCLUDED.product_line,
       category_id  = EXCLUDED.category_id,
       status       = EXCLUDED.status,
       in_stock     = EXCLUDED.in_stock,
       updated_at   = now();

    The update list never includes a BC-owned column (list_price_cad, available_in_ca, the rental and sale flags) or a seeded content column. That is what keeps each field with one owner.

  6. S6
    SQLMark the rows processedprocessed = true, processed_at = now()

    Query, same transaction as S5

    UPDATE staging.item_code
SET    processed = true, processed_at = now()
WHERE  load_batch_id = '0b9e…'
  AND  item_code     = 'MEG-1000';

    Done in the same transaction as the product write, so a crash part-way through means the rows are read again on the next run rather than skipped. Unmatched and unchanged rows are marked processed too.

Business Central

ERP-Sync Job, Custom API pull

  1. B1
    GETPull CAD price, availability and sale flagBC Custom API · item price endpoint · role = 'sale'

    For each BC sale item the job needs four values: the item number, the CAD unit price, whether it's available in Canada, and whether it's blocked for sale. The item number is matched through product_erp_refs with source_system = 'BC' and role = 'sale'.

    Write, BC-owned columns only

    UPDATE catalog.products
SET    list_price_cad  = 1015.00,
       available_in_ca = true,
       sale_enabled    = true,      -- false when BC blocks the item for sale
       updated_at      = now()
WHERE  sku = 'MEG-1000';

    BC is required for jmtest: a product with no BC sale record has no CAD price and can't be bought on jmtest.ca.

  2. B2
    GETPull rental items and replace rate tiersproduct_rental_rates · rental_enabled · rental_units_available_ca · role = 'rental'

    A product sold and the same product rented are usually two BC records, so rental items are matched with role = 'rental'. Rates are a table rather than columns because the number of tiers is a BC decision. They are replaced, not merged: after the run a SKU's tiers are exactly what BC has now.

    Replace, one transaction per SKU

    BEGIN;
DELETE FROM catalog.product_rental_rates
WHERE  sku = 'MEG-1000' AND region = 'CA';

INSERT INTO catalog.product_rental_rates
       (sku, region, period, rate, currency, min_periods, deposit, bc_item_no, erp_status, synced_at)
VALUES ('MEG-1000', 'CA', 'day',    45.00, 'CAD', 1, null, 'RNT-MEG-1000', 'active', now()),
       ('MEG-1000', 'CA', 'week',  180.00, 'CAD', 1, null, 'RNT-MEG-1000', 'active', now()),
       ('MEG-1000', 'CA', 'month', 540.00, 'CAD', 1, null, 'RNT-MEG-1000', 'active', now());

UPDATE catalog.products
SET    rental_enabled            = true,
       rental_units_available_ca = 3,     -- null when BC doesn't say; never guess 0
       updated_at                = now()
WHERE  sku = 'MEG-1000';
COMMIT;

    When an item leaves the rental group in BC, the job deletes its rate tiers and sets rental_enabled to false, and the rental form disappears from the product page.

  3. B3
    GETPull calibration service pricescatalog.calibration_services · unique on bc_item_no

    Upsert by BC item number

    INSERT INTO catalog.calibration_services
       (id, level, bc_item_no, price_cad, price_usd, erp_status)
VALUES (gen_random_uuid(), 'iso17025', 'CAL-ISO-HV', 190.00, null, 'active')
ON CONFLICT (bc_item_no) DO UPDATE
SET    price_cad  = EXCLUDED.price_cad,
       erp_status = EXCLUDED.erp_status;

    Only prices come from BC. Which service applies to which product is decided by catalog.calibration_rules, kept by the calibration lab in Studio. A rule points at a service by calibration_service_id, so the id must stay the same across runs: that is why the upsert matches on bc_item_no and never re-creates the row.

  4. B4
    JOBReport what didn't matchunmatched Sage 100 + BC item numbers

    The run ends with one list of item numbers that have no row in product_erp_refs, from both sources. Nothing is inserted for them. JMTS IT owns the mapping, so the list goes to them (§9).

Seeders

Once, before go-live

  1. D1
    SEEDLoad the starting catalogwrites the CDB directly

    The Seeders are the only thing that writes the catalog without going through the ERP-Sync Job. They run once to fill catalog.products before the first sync, including the content fields neither ERP holds: slug, specs, media, attributes, tags, ribbon_tag and so on.

    Seeded rate tiers and price matrix rows are replaced, not merged, per SKU, the same rule the job uses. brand_id is 'jmtest' for every jmtest.ca product.

  2. D2
    JOBFirst ERP-Sync run takes overERP fields now owned by the job

    From the first run onward the job overwrites every ERP-owned column with live values. Running a seeder again must not overwrite them (§9).

How the calibration add-on is chosen

From the data model. The first match wins:

  1. Product override: a rule with this product's sku.
  2. Category and spec range: a rule for the product's category_id where the spec named in spec_attribute falls between range_min and range_max, for example test voltage in kV. Spec values come from products.specs.
  3. Category default: a rule for the category with no range.

priority breaks ties between rules at the same level. A rule with offered = false marks a product or range as not offered.

9Open decisions

Need an answer before build

Sage 100 to product mapping

§5 is a proposal. Category needs a lookup from the Sage name to a catalog.categories id.

SuggestConfirm §5 with JMTS IT and keep the category lookup as a small table the job reads.

Product names

catalog.products has no name column. Sage 100 has item_code_desc, but storefront names are usually written for customers.

SuggestUse content names from the Seeders, and use item_code_desc only as a fallback for new items.

USD prices from Sage 100

Staging carries standard_price and suggested_retail, but jmtest.ca prices in CAD from BC.

SuggestUse BC for every jmtest.ca price. Fill list_price_usd from Sage 100 only if another storefront needs it.

Which warehouses count

Staging has one row per warehouse. Not every warehouse may ship to Canadian customers.

SuggestJMTS IT lists the warehouses that count for jmtest.ca; the job ignores the rest when setting in_stock.

What “multi-vendor” means

The diagram says BC pricing is multi-vendor. The data model has no vendor table.

SuggestConfirm with the BC admin whether one item can have prices from several vendors, and which one the storefront shows.

Sync schedule

How often JMTS IT pushes and how often the job runs decides how fast a price change reaches the storefront.

SuggestAgree a schedule for each source and show the last sync time in the CMS.

Where the run report goes

Unmatched item numbers are reported, not inserted. Someone has to see that report.

SuggestA daily list to JMTS IT, who own product_erp_refs, plus BC failures to Application Insights.

Content after go-live

The Seeders load specs, media and attributes once. After that, someone has to edit them.

SuggestEdit content fields in the CMS, and make the seeders refuse to run once the catalog has synced rows.
