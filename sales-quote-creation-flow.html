Sales quote creation in Business Central

How a quote request from the storefront becomes a Sales Quote in Business Central, how the sales team sends it and turns it into an order, and what happens when Business Central can’t be reached.

Base URL https://api.businesscentral.dynamics.com/v2.0/{tenantId}/{environment}/api/v2.0

Written as {base} below. Every BC call sends Authorization: Bearer {access_token}; calls with a body also send Content-Type: application/json. Values in examples are illustrative.

The request is saved in the storefront database first, so it can never be lost. A background job then creates the quote in Business Central. Sending the quote and converting it to an order happen later, when the sales team is ready.

Save the request

apps/web, while the customer waits

  1. 0
    APPSave the request with an outbox rowcommerce.quotes · quote_items · integration_outbox

    The quote request, its lines and an outbox row are written in one transaction. The customer sees “We’ve received your request” as soon as it commits. Business Central is not called while the customer waits, so a BC outage never loses a request.

    Outbox row

    topic            'rfq.submitted'        -- proposed topic
aggregate_id     quotes.id
status           'pending'
attempts         0
next_attempt_at  now()

    Payload

    {
  "quoteNumber": "WEB-Q-2045",
  "currency": "CAD",
  "customer": { "company": "Acme Ltd", "name": "Sam Lee", "email": "buyer@acme.com" },
  "validUntil": "2026-12-11",
  "lines": [
    { "lineType": "purchase", "sku": "MEG-1000", "quantity": 5, "unitPrice": 129.00 }
  ]
}

    The data model’s outbox already plans for RFQs to “follow later”. rfq.submitted is the proposed topic name; the unique key (topic, aggregate_id) stops a double submit creating two rows.

Create the quote

jobs/integration-outbox, in the background

The job claims due rfq.submitted rows the same way as the orders flow: it pushes next_attempt_at forward five minutes as a lease, using FOR UPDATE SKIP LOCKED, so two runs never work on the same request. Every step below is safe to repeat.

3When the sync fails

Retry, then roll back and tell people

The request is already saved, so a failed sync never loses it. Errors that can fix themselves are retried; errors that can’t stop straight away. After the last attempt, the sales team is told and the request shows in the CMS with a Retry button.

Temporary or permanent?

The test: would the same request succeed later without anyone changing anything? If yes, it’s temporary and worth retrying. If no, retrying only delays the alert.

ResponseTypeWhat the job does
timeout, 429, 500, 502, 503, 504TemporaryRetry with backoff. For 429, wait at least the Retry-After time.
401Temporary, onceGet a new token and retry. A second 401 is permanent and alerts IT.
400, 404PermanentStop. The data is wrong, for example a SKU with no BC item number.
403PermanentStop and alert IT. The app is missing permissions in Business Central.

Retry schedule

Failureattempts afterNext try
1st1in 1 minute
2nd2in 5 minutes
3rd3in 15 minutes
4th4in 30 minutes
5th5No retry. Roll back, mark failed, notify.

What is recorded

Everything about a failure is kept on the request’s row in commerce.integration_outbox: attempts counts failures, next_attempt_at holds the next retry time, last_error keeps the latest BC error, and status becomes failed when the job gives up. The proposed quotes.bc_sync_status column mirrors it as pending, synced or failed, so the CMS can show the state without reading the outbox. The rollback finds any partial quote by externalDocumentNumber, so no BC ID needs storing for it.
