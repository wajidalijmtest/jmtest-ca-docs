Catalog: how products get into the Consolidated Database

Three sources feed the catalog: Sage 100 items, Business Central CAD pricing, and a one-time seed. Sage 100 items and Business Central prices both pass through the ERP-Sync Job. Only the Seeders write to the Consolidated Database (CDB) directly.

1The whole flow

Three sources, one writer

JMTS IT pushes the Sage 100 item extract into staging.item_code, a temporary store the storefront never reads. The ERP-Sync Job reads the new staging rows, pulls CAD pricing and the other Canadian fields from the Business Central Custom API, and writes the result into the catalog tables. The Seeders ran once to load the starting catalog. After that, every change comes through the ERP-Sync Job.

Source system Staging table Writes to the CDB Consolidated Database
Only two things write the catalog.Sage 100 items and Business Central prices both pass through the ERP-Sync Job. Only the Seeders write to the CDB directly, and only once. Nothing else, including the storefront and the CMS, changes ERP fields.

3Step by step

Sage 100 items

JMTS IT push, then the ERP-Sync Job

  1. S1
    PUSHJMTS IT pushes the item extractstaging.item_code

    Each push run gets one load_batch_id. Rows are unique on (item_code, warehouse_code, load_batch_id), so there is one row per item per warehouse per push. It uses the same push contract as Vaetrix (docs/infra/staging-item-code.sql).

    Example row

    item_code             'MEG-1000'
item_code_desc        'Insulation tester, 10 kV'
product_line          'INSUL'
category              'Insulation testers'
sales_uom             'EA'
standard_price        725.0000
suggested_retail      799.0000
quantity_on_hand      4.0000        -- per warehouse; null = unknown
warehouse_code        '000'
item_status           'Active'
source_system         'SAGE100'
load_batch_id         '0b9e…'
row_hash              'a41f…'       -- hash of the business columns
processed             false

    Fields that aren't mapped to a column are kept in raw (jsonb), so nothing in the source record is lost.

  2. S2
    SQLRead unprocessed rowsstaging.item_code WHERE processed = false

    A partial index on unprocessed rows keeps this read fast however large the staging table grows.

    Query

    SELECT *
FROM   staging.item_code
WHERE  processed = false
ORDER  BY loaded_at;
  3. S3
    JOBMatch each item to a storefront SKUcatalog.product_erp_refs, source_system = 'SAGE100'

    The Sage 100 item_code is looked up as native_number in catalog.product_erp_refs. Item numbers with no row there are reported, not inserted: JMTS IT decides whether they belong on the storefront and adds the mapping.

  4. S4
    JOBUpdate the product when something changedcatalog.products

    The job compares row_hash with the last processed row for the item, and writes to catalog.products only when it changed. Which Sage 100 columns map to which product columns is still to confirm (§5).

  5. S5
    SQLMark the rows processedprocessed = true, processed_at = now()

    Rows are marked only after the product write has committed, so a crash part-way through means the rows are read again on the next run rather than skipped.

Business Central pricing

ERP-Sync Job, Custom API pull

  1. B1
    GETPull CAD price and availabilityBC Custom API · item price endpoint

    Writes list_price_cad, available_in_ca and sale_enabled on catalog.products. BC item numbers are matched to SKUs through catalog.product_erp_refs with source_system = 'BC' and role = 'sale'.

    BC is required for jmtest: a product with no BC record has no CAD price and isn't sold on jmtest.ca.

  2. B2
    GETPull rental items and ratescatalog.product_rental_rates · rental_enabled · rental_units_available_ca

    Matched through product_erp_refs with role = 'rental', because a product sold and the same product rented are usually two BC records. Rates are replaced, not merged, per SKU: the rate tiers for a SKU are always exactly what BC has now.

    One row per rate tier

    sku          'MEG-1000'
region       'CA'
period       'week'          -- 'day' | 'week' | 'month'
rate         180.00
currency     'CAD'
min_periods  1
deposit      null
bc_item_no   'RNT-MEG-1000'
erp_status   'active'
synced_at    now()
  3. B3
    GETPull calibration service pricescatalog.calibration_services

    One row per BC service item: level (nist or iso17025), bc_item_no, price_cad and erp_status. Which service applies to which product is decided by catalog.calibration_rules, kept by the calibration lab, not by this job.

Seeders

Once, before go-live

  1. D1
    SEEDLoad the starting catalogwrites the CDB directly

    The Seeders are the only thing that writes the catalog without going through the ERP-Sync Job. They run once to fill the catalog before the first sync. Seeded rate tiers and price matrix rows are replaced, not merged, per SKU, the same rule the job uses.

    After the initial load the ERP-Sync Job owns every ERP field. Running a seeder again must not overwrite values the job has already synced (§5).

5Open decisions

Need an answer before build

Sage 100 to product mapping

The data model lists the staging columns but not which product column each one fills: name, category, status, stock.

SuggestWrite the column-by-column mapping with JMTS IT and add it to this page.

USD prices from Sage 100

Staging carries standard_price and suggested_retail, but jmtest.ca prices in CAD from BC.

SuggestUse BC for every jmtest.ca price, and use the Sage 100 prices only for list_price_usd, if at all.

What “multi-vendor” means

The diagram says BC pricing is multi-vendor. The data model has no vendor table.

SuggestConfirm with the BC admin whether one item can have prices from several vendors, and which one the storefront shows.

Sync schedule

How often the ERP-Sync Job runs, and how often JMTS IT pushes to staging, decides how quickly a price change reaches the storefront.

SuggestAgree a schedule for each source and show the last sync time in the CMS.

Where unmatched items are reported

Item numbers with no row in product_erp_refs are reported, not inserted. Someone has to see that report.

SuggestSend a daily list to JMTS IT, the owners of the mapping.

Running the Seeders again

If a seeder is re-run after go-live, it could overwrite prices and flags the ERP-Sync Job has synced.

SuggestMake the seeders refuse to run once the catalog has synced rows, or skip ERP-owned fields.
